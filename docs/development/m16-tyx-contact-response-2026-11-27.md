# M16 GPU geometry refinement and contact response

This continues the saved-pose mesh-query work on `feat/tyx-mesh-contact-query`.
It adds real TYX CUDA geometry refinement, elliptic contact response and a
separate coupled acceleration workspace. It does **not** enable the original
M16 dynamics compiler, integrate a trajectory or qualify PPO.

## Geometry correction

The thin-simplex cases lost FP32 precision in Gram determinant subtraction and
in the cancellation of long tangential components. The shared GJK/EPA kernels
now use compensated products, geometric cross-product barycentrics and
plane/segment projections. Iteration limits and original hulls are unchanged.

The mesh workspace additionally applies a finite-feature CUDA refinement only
to unresolved pairs whose two hulls each have at most 16 vertices. Complete
face/edge axes and vertex-triangle/edge-edge closest features preserve original
vertex identities and convex geometry. A result is published only when its
support bound, witness closure and bracket satisfy the fixed 5 micrometre
geometric criterion. Larger unsupported cases remain explicit failures.

In the original eight saved M16 reset poses:

| Check | Before this change | Final |
|---|---:|---:|
| Candidate pairs | 51,666 | 51,666 |
| Independently certified | 49,813 | 51,666 |
| Published but failed independent check | 722 | 0 |
| Unresolved | 1,131 | 0 |

The maximum gap discrepancy against the independent original-vertex FP64
support/SAT check is 8.7446e-8 m. All original native contact pairs remain in
the candidate set. This is a finite saved-pose result, not arbitrary-trajectory
coverage or a proof that all convex pairs converge.

`MeshQueryResult.device_view()` lends existing GPU arrays in a context manager.
It validates publication and witnesses before lending; it refuses unresolved
geometry, expired results, overwrites and close while borrowed. Only the small
count/error vector is downloaded, not all contact geometry. The arrays remain
logically read-only and cannot be retained beyond the borrow scope.

## Elliptic contact force and friction

`_elliptic_contact.EllipticContactWorkspace` consumes residual acceleration
`J*qacc - aref`, original inverse regularization D, two friction coefficients,
mu and explicit row eligibility. `evaluate_device` accepts resident TYX arrays;
`evaluate` and `read` are explicit host diagnostic conveniences.

The condim-3 elliptic cost, force and Hessian follow MuJoCo 3.3.7
`engine_core_constraint.c::mj_constraintUpdate_impl`, including the satisfied,
quadratic and cone regions. Original regularization compatibility is checked.
Invalid parameters or ineligible geometry produce invalid status and cleared
outputs, not an apparently valid zero-contact result. This is not a penalty
spring or a pyramid approximation of the elliptic cone.

For 4,154 actual active contact inputs from the eight original saved poses,
CUDA force, Hessian, cost and region state all passed native comparison.
Maximum force and Hessian absolute errors were 2.818e-8 and 2.186e-8;
cost error was 2.523e-8. These inputs were captured from native forward
evaluation without integration; they were not generated by the new mesh query.

## Coupled acceleration and precision

`_elliptic_dynamics.EllipticDynamicsWorkspace` solves the primal acceleration
objective with physical M, elliptic contacts, scalar equality, DOF friction
loss and joint/tendon limits. It uses bounded Newton iterations and a convex
directional-derivative bisection search. The algorithm does not reproduce
native iteration order, warmstart or stopping rules.

The original scene has large smooth accelerations and an approximately
1.235e6 mass condition number. Converting an already-converged native
acceleration to one FP32 value alone breaks the predeclared normalized
force-balance check in all eight saved worlds. Simply increasing iterations
did not resolve this representation problem.

The device implementation now solves for a correction around the smooth
acceleration, uses compensated products/sums, and retains high/low FP32 lanes
for the smooth acceleration, correction and output. This uses the pinned TYX
FP32 CUDA runtime; it does not call a CPU solver or claim hardware FP64 kernels.
Consumers must preserve `acc` **and** `acc_low`. Summing them into a single
FP32 array reintroduces the demonstrated error.

The final eight-world check includes 4,154 contacts and 24 scalar rows
(equality and friction loss). All worlds converged in 9–10 Newton iterations
within the original bound of 100. Independent original-native-array force
balance was at most 2.5425e-7, below the predeclared 2e-6 criterion. Maximum
acceleration absolute discrepancy was 9.650e-5 and passed the predeclared
componentwise criterion. Earlier failed numerical experiments are retained.

All inputs and Newton scratch remain on the device during a solve. Explicit
diagnostic downloads and a small status read at consumer admission remain.
`AccelerationResult.device_view()` refuses an unconverged or invalid batch,
guards buffer lifetime and exposes active counts with the paired output.
This is an experimental acceleration interface, not an engine `step` API.

## Validation and remaining integration

The shared convex kernels were checked with a 172-test suite requiring actual
CUDA execution for its device cases (host preflight tests are included). After later
interface/solver edits, the final targeted geometry/response/dynamics suite
passed 20 tests; the unchanged shared-kernel coverage is retained. Fixtures
include original thin pairs and two originally nonconverging coupled worlds.
Negative checks cover invalid geometry/parameters, exhausted iteration budget,
unsupported scalar rows and expired/borrowed buffers. Software tests and
saved-state queries add zero integration steps, policy samples or PPO updates.

The original dynamics compiler still rejects unsupported engine combinations.
The following work remains before M16 GPU learning:

1. Generate the complete device contact manifold/frame/Jacobian/impedance from
   GPU geometry and device kinematics. A single certified pair witness is not
   automatically the complete original manifold. The current acceleration
   validation uses native-captured constraint inputs.
2. Integrate the original mocap, coupled joints, summed actuator clamping and
   IMPLICITFAST semantics. Preserve paired state precision through integration.
3. Attach device PD, observations, reward, termination/local reset and rollout,
   then bridge the existing policy/Adam without diagnostic actions or RNG reset.
4. Validate the resulting complete engine and learning candidate under the
   existing release/review/resource/lineage procedure before bounded PPO and
   8→32→256 scaling. These measurements are not end-to-end training throughput.
