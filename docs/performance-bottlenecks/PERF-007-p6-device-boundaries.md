# PERF-007：P6 设备算术适配的边界调用成本

- 状态：调用结构与公开计数已确认；细项性能归因未完成。
- 位置：`backends/tyx_math.py::TyxMath.call`、`tyx_participants.py::_RobotPort`、
  `tyx_articulated.py::TyxNodeRobotConstraints`。
- 范围：P6 FP32计算/FP64存储，公开 tyx 同步适配；当前固定依赖99f6df7c。

## 已观察事实

2026-10-28实际CUDA解析单对场景：质量2的Y滑块、逆质量1的节点，节点y=.09、球半径.1，h=.01。
一次完整step接受，位置/速度各1轮，报告残差0；公开计数为80次launch及完成、570次上传、168次下载。
这不是80个单独CUDA计时样本，上传/下载也不是字节数。

当前每次kernel调用独立创建输入/输出缓冲区、同步和下载；点端口反复查询FK/J/M，材料诊断还会重新求设备能量。
工作区关闭后只允许编译缓存保留，不保留隐藏物理状态。这些是phymeo设计选择，不能直接归为tyx实现缺陷。
候选热点包括调用/分配、IR或编译缓存查询、同步、密集小矩阵和主机独立审计；尚无profiler占比。

模块测试耗时包含首次编译、pytest以及部分并发验证，例如T4全部13项C++127.12s、CUDA7.18s；
这些不同工作负载/缓存口径的数据不构成后端加速比，也不能用来宣称Warp差距。
内存峰值、传输字节量、纯kernel稳态耗时均未测，不填0。

P6最终审阅发现材料运行期误差门禁缺失，修复版每次设备材料求值后独立执行FP64内力/能量验收；这属于生产正确性成本，正式step计时必须包含，不能为提高结果而关闭。此前候选S2 CUDA完整200帧约1200.27s，和其他测试并发且属于修复前源码，只是探索记录，不是正式串行性能证据。旧C++集成批次超过45分钟仍有新编译子进程，后因源码修复主动终止，未计通过；尚未分离首次编译、缓存和运行期成本，不能归因tyx实现缺陷。

## 已定位：受限环境的默认编译缓存不可写

通过仅用tyx公开API的[复现](repros/p6_cache_probe.py)和[原始JIT记录](measurements/p6-cache-probe.json)确认：同一个4元素C++ kernel，在默认缓存下连续创建两个Runtime，各自首次调用均为cold_compile、reason为cache_write_failed；同Runtime第二调用为process_hit。将cache_root显式设到工作区，第一Runtime正常cold_compile，第二Runtime首次为artifact_hit；所有结果均正确。

这是当前受限运行环境的默认缓存目录写入失败，不能登记为tyx实现性能缺陷。后续验证统一设置`TYX_CACHE_DIR`到工作区`artifacts/tyx-cache`，并保留`TEMP/TMP=artifacts/tmp`。使用依赖已有公开缓存能力是环境构建修正；不改变算法、工作区物理状态寿命、精度或事务。此次探针存在其他并发负载，JIT时长只作诊断，不作为正式性能基线或Warp差距。

默认缓存失败会使phymeo每子步重新创建Runtime时再次编译，因此此前默认环境的完整场景耗时和超长C++批次不能与修复缓存环境混为一组。正式性能报告必须记录缓存路径、冷/热含义；依赖缺陷仍需要可写环境中的最小复现。
