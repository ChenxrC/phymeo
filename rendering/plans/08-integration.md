# 上下游合并与联调

集成人维护候选分支、共享夹具、集成测试及安装配置。每个模块在自己的工作树开发并提交；涉及公开字段的调整先落在所属模块，再由下游合入这次调整。G1 的[静态清单与双帧测试](../tests/integration/test_scene_source.py)及[腕部标定与错帧测试](../tests/integration/test_camera_capture.py)已落地。G2 的[拍摄会话联调](../tests/integration/test_backend_contract.py)使用真实程序数据源、请求规划器和发布校验，设备读回由测试记录器提供。G3–G5 待执行。

## 在哪些边界接起来

| 生产者 → 消费者 | 交接内容 | 跨模块测试与通过条件 |
| --- | --- | --- |
| M1 → M2/M5 | 网格单位、资源标识、PBR 材质、静态清单 | 同一网格两个实例只改变实例变换；尺寸、两个正 ID 及材质与夹具一致。删除一条资源引用后能定位具体实例和资产，整次开场失败。 |
| M7 → M2 → M3 | `SceneSource` 给出 `VisualScene` 和有序 `SceneFrame`；曝光取同一帧的腕部位姿 | 对两帧不同转腕姿态分别核六个帧键字段及时间；局部偏移只乘一次。相邻帧交换相机、交换世界或复用 reset 前曝光均拒绝；快照读取前后物理步数差为零。 |
| M3/M6 → M4 → M5 | 完整 `CaptureRequest`，包括相机、路径和**全部**请求通道；原生设备消费有序阶段 | 在同一构图上分别请求仅 RGB、仅传感通道、联合通道。支持表为真的组合能完整交付，缺任一请求能力时显式拒绝整次请求；整数通道和深度跳过显示变换。 |
| M2/M5 → M6 → 消费者 | 场景、帧键、时间与曝光共同绑定的 `Capture`，每个通道的独立字节 | 以独立解码器查通道集合、布局、长度、四个角、中心前景点和背景约定；再拍一帧、关闭会话后首个帧包字节不变。交错两会话并故意给错场景键，检查原有帧包不受影响。 |
| M7/M5 → 回放、训练相机 | 按世界、代次和相机区分的帧，无隐式步进；历史积累按有效来源管理 | 与单世界同配置作对照。只重置一个世界、跳切相机或更换静态清单，目标历史失效，其余世界的帧键、深度和标签仍与对照一致。 |

共享样本位于 [rendering/tests/fixtures/g1](../tests/fixtures/g1/README.md)，记录网格来源、单位、资产哈希和两次曝光的独立预期值。模块作者可先用单测中的微型样本。单测桩只用于检验协议、错误路径和字节格式。设备和整机验收读取真实后端产生的帧。

**避免互相等待。** G2 中 M4 可先用记录阶段顺序的 M5 测试替身联调；M5 启动真实设备时再由集成人验证提交、同步和像素。M7 可以先并入程序场景，R1 再并入真实资产和轨迹，R4 再并入多世界源。M1/M2 对纹理、环境光源的向后兼容扩展，可作为第二次交接在 G4 准备 R2 时合入；第一张标定桌使用现有不透明材质和方向光。

## 候选分支合并次序

| 关口 | 所需模块与合并顺序 | 集成人在合并候选上执行 | 放行范围 |
| --- | --- | --- | --- |
| G1 · 输入合同 | 先 M1，再 M2，再 M3。三者可先并行开发；集成人发布共同夹具版本 | 模块单测；集成 `test_scene_source.py` 中的静态清单与手写双帧部分，`test_camera_capture.py` 中的解析投影部分 | 允许下游依赖场景键、节点变换和曝光约定 |
| G2 · 拍摄合同 | M6 接 G1；M4 接 M3/M6；M7 的程序场景接 M1/M2（可独立先并入候选）。M5 的公共会话接以上接口 | 各自单测；`test_scene_source.py` 走真实程序适配器，`test_backend_contract.py` 检查请求、能力与会话拒绝行为。M5 测试桩与真实后端结果分别记录 | 允许图形设备接入；尚不能签收首图 |
| G3 · 两条真实成像路径 | M5 参考后端和原生光栅各自形成可独立审查的提交；共享接口只由 M5 负责人维护 | `test_reference_table.py` 和 `test_native_table.py`。执行 R0，分别记录实际后端／路径。参考端双路径先通过时可保存可行性样图；G3 合并放行还需原生光栅在同一桌面通过 | 拿到同一输入的真实样图、深度和标签，允许开始机器人端到端验收 |
| G4 · 真实场景与观测 | M1 视觉资产、M7 真实轨迹适配先接合，通过 R1 后在同一候选上分别合 R2 和 R3 | `test_panda_replay.py`、真实设备上的 `test_camera_capture.py`、R2 画质与计时。两条线都要保存证据，合并其一后对另一条按影响复核 | R0–R3 齐备，可交付单世界最小闭环 |
| G5 · 多世界及打包 | G4 完成后接入 M5/M7 的多世界调度、隔离和消费端读回，再从同一提交构建 wheel | `test_multiworld.py` 对照 1、2、8 世界，并从源码树外用 wheel 重放标定桌和测试部署配置 | 按最终验收单逐项签收，可声明首版支持的设备、能力组合和部署方式 |

上述 `test_*.py` 指各关口未来的 `rendering/tests/integration/` 文件，同一个文件可分阶段添加用例。设备测试始终记录真实实现名。G1/G2 期间尚未开发的设备用例留在后续关口新增；到所属关口缺设备、样本或用例时记录“阻塞”，不能计作通过。

## 每次如何合并

1. **创建候选。** 集成人从 `codex/rendering` 的计划提交创建独立集成工作树；开发者从已公布的合同基线创建模块工作树。派工登记模块、负责人、基线和拥有的路径。公共包导出、`rendering/pyproject.toml`、共享夹具及跨模块测试的修改统一交集成人。
2. **提交交接。** 模块负责人给出提交号、基线、文件清单、精确的测试选择和原始结果。明列所用桩、实际后端和尚未接合的消费者。对接口的修改附新旧实例输入和消费者如何迁移。无关改动留在原工作树。
3. **逐项合并。** 集成人确认前置提交已进入候选，在同机唯一验证队列上按表合一个逻辑变更，执行受影响的模块测试和该边界正反例。在新旧合并组合上记录候选提交、环境、命令和退出码。已经验证的相同代码与环境可引用既有记录。
4. **故障定位。** 保存失败输入、截至哪一帧、预期值、实际值及首个出错边界。输入已错交 M1/M2/M3/M7；像素身份正确但通道或布局错误交 M5/M6；原生阶段漏执行交 M4/M5。修正在原责任分支提交，以同一固定输入复核，并重测受影响的下游。
5. **隔离失败与收口。** 失败的改动停在候选上；若已合并且阻塞无关模块，通过明确的反向提交移出该逻辑改动，保留开发历史和证据。并行模块继续在可用基线上工作。最后由一名集成人复核[验收规程](09-acceptance.md)和待合并的实际提交。

接口争议优先用最小输入复现。例如 ID 错位，先解码手写的 2×2 标签图，再比较后端的同布局读回，最后才查 Panda 模型。一个上游错误只修一次；改动触及坐标、色域、帧键或像素布局时，沿表重验每个受影响消费者。
